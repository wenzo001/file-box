# 无痕传输（Ephemeral Transfer）

一条独立的文件通道：发送方选文件 → 生成一次性传输码 → 接收方在另一台设备输入码 → 端到端加密分块传输。
它不写入正式文件库（`uploads/`），不进文件列表，不产生永久分享链接。

- 入口：首页顶栏「无痕传输」→ `public/transfer.html`
- 代码：`public/transfer.html`（页面）、`public/xfer-engine.js`（会话引擎/通道适配器）、
  `public/xfer-proto.js`（协议与密码学，浏览器与 Node 共用同一份）、`public/xfer-worker.js`（加密封装的工作线程）、
  `lib/transfer.js`（服务端：会话、信令、密文中转）、`test/transfer.test.js` + `test/big.test.js`

## 1 架构

```
                发送端浏览器                          服务端                     接收端浏览器
  ┌────────────────────────────────┐      ┌────────────────────────┐   ┌────────────────────────────────┐
  │ transfer.html  (UI/进度/状态)  │      │ lib/transfer.js        │   │ transfer.html                  │
  ├────────────────────────────────┤      │  /api/xfer/*           │   ├────────────────────────────────┤
  │ xfer-engine.js  Session        │◀────▶│  会话账本 / 信令 / 密文 │◀─▶│ xfer-engine.js  Session        │
  │   状态机 · 三级进度 · 续传      │ SSE  │  转发（只懂帧头长度）  │SSE│   状态机 · 补拉缺块 · 落盘校验 │
  ├────────────────────────────────┤      └────────────────────────┘   ├────────────────────────────────┤
  │ xfer-proto.js  封帧/密钥/清单   │ xfer-worker.js                    │ xfer-proto.js  开帧/验标签      │
  │  (AES-256-GCM, HKDF, SHA-256)  │◀══ 加解密在工作线程，主线程不卡 ▶══│  (xfer-worker.js 同上)          │
  └────────────┬───────────────────┘                                 └───────────────┬──────────────────┘
               │  通道 1：WebRTC DataChannel（点对点，字节不过服务器）                 │
               │  通道 2：WebRTC DataChannel over TURN 中继（字节不过本服务器）        │
               └───────────────────────┼──────────────────────────────────────────────┘
                          通道 3：服务端密文中转（seg 上传/拉取，服务器只见密文帧）
```

三个通道只是**适配器**：加密、分块、进度、续传逻辑全在 `xfer-engine.js` 一份实现里，任何通道都不会绕开它。
明文从不离开发送端浏览器；服务端与 WebRTC 对端拿到的都是同一种帧（见 §3）。

## 2 状态机

两个维度分开走，UI 同时显示。

**phase（会话进度）**

```
idle → fingerprinting → waiting ──▶ pairing ──▶ transferring ──▶ verifying ──▶ ready → saving → done
                          │            │             ▲   │                       （接收端）  （发送端 done）
                          │            ▼             │   ▼
                          │        retrying ─────────┘  paused
                          └─ 任何阶段：cancelled（任一方取消）/ failed（不可恢复错误）
```

| phase | 含义 |
|---|---|
| `fingerprinting` | 只在本地读文件算 SHA-256，尚未上传任何字节 |
| `waiting` | 会话已建，等接收方输入传输码 |
| `pairing` | 已配对，正在派生/核对密钥与安全码 |
| `transferring` | 加密分块推进中 |
| `paused` | 用户暂停；服务端状态与本地暂存全部保留 |
| `retrying` | 连接断了，正在自动重连或改走中转 |
| `verifying` | 全部到齐，逐块验标签 + 算总 SHA-256（仅接收端） |
| `ready` | 校验通过，此时才允许显示文件名并保存（仅接收端） |
| `saving` / `done` | 解密写盘中 / 完成 |

**channel（当前走哪条路）**：`none → p2p_connecting → p2p | turn_relay | server_relay`。
`p2p` 只在 ICE 选中的候选对两边都不是 relay、且 DataChannel 真的 `open` 之后才报；
TURN 中继报 `turn_relay` 并明确写"不是直连"，绝不当成直连。

**进度分三档，不是一条线**：`sent`（发送端已发出）→ `uploaded`（中转区已收到）→ `stored`（接收端已验标签并本地落盘）。
只有 `stored` 算接收完成进度；通道切换用的是同一批 `Set`，不会倒退、不会重复计入。

## 3 加密协议与密钥生命周期

全部用浏览器 WebCrypto（`crypto.subtle`）或 Node `crypto`，没有自研算法。
HTTP 入口（非安全上下文）没有 WebCrypto 时，走同一套接口的纯 JS AES-GCM 实现，并在工作线程里跑；
此时两端能力会都落到 `kex='code'`，UI 上明确标出来。

```
传输码 = sid(8 字符，公开) + secret(24 字符，永不发送)，字母表正好 32 个（26 个字母去掉 i/l/o + 数字 1–9），
         一字节取低 5 bit 无偏映射 → secret 有 120 bit 熵
   │
   ├─ proof = HMAC-SHA256(key="filebox-xfer-v1/proof|"+sid, msg=secret)   ← 只有两端能算出来
   │      └ 服务端只存 proof 的 SHA-256，凭它验配对；拿不到 secret，也反推不出码
   │
   ├─ ECDH(P-256) 临时密钥对（安全上下文）→ shared secret
   │      非安全上下文退回 kex='code'（没有前向保密，也不独立抵御主动冒充的服务器，UI 上明写）
   │
   └─ HKDF-SHA256(ikm=shared, salt=transcript, info 各不同) ─┬─ kRec   文件密钥的根
        transcript = SHA-256("filebox-xfer-v1|"+sid+"|"+kex+"|"+两端公钥)   ├─ kMeta  清单帧的密钥
                                                            ├─ kConfirm 配对确认
                                                            └─ 安全码 5 位（两端各显示一次，人眼核对有没有中间人）
   文件密钥 = HKDF-SHA256(kRec, sid8, 'file-v1|'+sid+'|'+fileId)   ← 每个文件独立，绑定会话
   confirm  = HMAC-SHA256(kConfirm, "filebox-xfer-v1/confirm|"+role+"|"+sid)
   传输码本身从不直接当文件密钥用。
```

**帧格式**（`0xfb` + 版本 + 类型 + fileId(4) + chunkIdx(8) + plainLen(4) ‖ 密文 ‖ GCM tag(16)，帧头 19 字节）：

- AES-256-GCM，明文块固定 128 KiB（最后一块为余数）。
- nonce(12B) = `0x78 | type | fileId(4B) | chunkIdx 的低 6 字节(48bit)`，**完全由 (类型, 文件号, 块号) 决定**：
  同一块重传、断点续传、换通道，产生的字节一模一样 → 不存在 nonce 重用，也不会出现"两份不同密文对同一 nonce"。
- AAD = 帧头 + `sid8`：把会话号、文件号、块号、协议版本都绑进认证标签，
  跨会话拼接、分块重排、改内容、改长度、截断，全都在开帧时失败。
- 清单（文件名、相对路径、大小、每块长度、SHA-256）本身是 type=1 的加密帧，用 `kMeta`，服务端读不到。
  相对路径必须在清单里：只给文件名的话，同一批里不同子目录下的两个同名文件在接收端就是同一个东西。
- 接收端先验 GCM 标签再用这块；整文件收齐后再逐块开一遍，比对每块长度、总长度、以及
  "分块 SHA-256 串联后的再哈希" == 清单里的 `sha256`，全部通过才 `verified`。

**密钥只在两端**：服务端 API 没有任何一个接口能递交或取回明文密钥；
刷新后能续传，靠的是浏览器自己 localStorage 里的派生结果，不经过服务器。

## 4 自动降级

| 触发 | 行为 |
|---|---|
| 安全上下文 + 有 WebRTC | 先试直连：trickle ICE 交换候选，`p2pTimeoutMs` 内没开成 DataChannel 就转服务器中转 |
| HTTP 入口 / 没有 WebCrypto / 没有 RTCPeerConnection | 直接服务器中转（仍然全程应用层加密，只是慢一点、多一跳） |
| `failed` / `closed` | 关掉 rtc，立刻转 `server_relay`，继续用同一批帧、同一套进度集合，不重发已确认的块 |
| `disconnected` | **先等，不立刻降级**。切网、休眠唤醒、ICE 重选常常几秒内自己回到 `connected`；给 `dcRegraceMs`（默认 5 秒）宽限，期间一旦 `open` 就作废这个念头，到点仍不通才降级 |
| 直连建链超时（`p2pTimeoutMs`，默认 8 秒） | **两端都要改标**。以前只有发送方到点认输，接收端界面能一路停在"正在尝试直连"，而它其实全盘在从服务器拉密文，那条开不了的 pc 也一直悬着不关。**现在超时不再掐死那条 pc**：先把进度切到中转推起来，直连在后台继续试（`lateRtcMs`，默认 120 秒）；它一旦 `open`，通道标识与后续帧立刻切回直连 |
| **DataChannel 缓冲满（背压）** | **不是降级理由**。`bufferedAmount` 越过 4MB 高水位就等，等它跌回 1MB 低水位（`bufferedamountlow` + 100ms 轮询双保险）再续发；连续 30 秒排不动才算链路失效并降级 |
| 配了 TURN 且拿到短期凭证 | ICE 候选里带 TURN；选中候选对是 relay 类型 → 报 `turn_relay`（UI 写明"不是直连"） |
| 发送方建 rtc 时还没配对、`/turn` 回 409 | rtc 必须先于事件流建好（否则会漏掉对方的 offer）。收到 `joined` 之后再补取一次凭证，用 `setConfiguration` 把 relay 服务器加进正在进行的 ICE；否则发送方永远只有本机候选，TURN 形同虚设 |
| TURN 拿不到 / 被防火墙挡 / 仍然不通 | 转服务器中转；三方都不行 → `retrying`/`failed`，给出可操作文案，不会无限等 |
| 中转区写入失败、429 太忙 | 指数退避重试 5 次，再失败就把错误报给用户并且可以续传 |
| **单个请求挂住不返回**（socket 死了但连接没断，`fetch` 既不 resolve 也不 reject） | 每个请求都带 `netTimeoutMs`（默认 30 秒）到点 `abort` 并按"可重试"重投这一块。**没有这层超时时会整段静默停摆**：那一个请求永远占着发送窗口的一个并行槽，槽被吃满之后进度不再动、界面也不报错（2GB 实测停在 506/16385 块，服务器只有 66MB，接收端已把服务器手上的块全存完了）。重投是幂等的：nonce 由 `type/fileId/chunkIdx` 决定，同一块重发的字节完全一样 |
| **收尾（`POST /api/xfer/done`）被拒或挂住** | 只认服务器的答复：409 / 超时都按退避重投（最多 4 次），**服务器收下了才把相位落到 `done`**。以前是"请求发出去就算完成"，实测出来的形状是 `界面说完成 / 服务器账本还写着 paired` —— 密文不会被清、中转配额一直占着，同时对用户撒了谎。四次都不成时留在"可以继续"的档位上，说"这一单内容都传完了，但服务器没收下收尾"，不报死 |
| **发送端长时间没有任何一块有进展** | 主循环带 `stallMs`（默认 60 秒）看门狗：`sentFrames / acked / cursor` 三个量都不再动，就**先试着自己恢复**（退出当前发送循环、隔 `retryGapMs` 重进，最多两次），两次都不回到"真的又发出去过块"才报"传输卡住了…点继续接着传"并停在那一档，不再每 300ms 空转等一个永远不来的东西。先自己试的理由：慢线程、瞬时链路这类卡住多数会自己过去；而**预算只在真的发出去过块时才还**，否则 worker 被杀那一类不可自愈的卡住会变成按 `stallMs` 一轮的无限重试 —— 那正是这条规则要消灭的东西。成因不止网络 —— **加密线程被浏览器杀掉**（`postMessage` 发出去、`onmessage` 再也不来）也是这个形状。两条边界：用户按暂停**不算**卡住（计时基准跟着挪，否则"暂停一分钟后继续"会被报成故障）；"发完了等对方逐块校验"那一段**不由这把尺子量**（GB 的校验本身就要几分钟，它有自己的 1200×500ms 上界） |
| 重算校验时某一块从 IndexedDB 读不回来 | **不是降级理由，也不是"文件坏了"**：那一帧服务器手上还有 —— 先补拉这一帧、重新落盘再继续。补拉也拿不到才报"本地和服务器都读不到了，请让对方重发一次"。（600MB 实测：4801 帧全收齐，却卡在第 1799 块的读失败上，整单被判"合成错误"） |
| 降级之后才迟到的 `offer` / `answer` / `ice` | 收下就算，直接丢掉。此时 rtc 已经关了，拿着 null 去 `takeOffer/takeAnswer` 会把一句 TypeError 顶到用户界面上——传输其实还在正常走中转 |

背压这一条单独说：以前"缓冲满了"和"通道没了"走的是同一个分支，于是健康的直连一旦被对端
读取速度堵住，剩下的整份文件都会被"额外"PUT 进服务器中转区（界面还写着"直连"）。
现在两者分开，并且发送端会记 `dcFrames` / `relayFrames`：一个字节都没走通道的情况下，
通道标识会立刻如实改成 `server_relay`，不会停在"正在建立直连"。
慢确认也不再被当成丢包 —— 同一帧两次重发之间至少隔 `retryGapMs`（5 秒）。

TURN 凭证是服务端按 coturn 的 REST API 口令方式现算的短期凭证：`username = 过期时间戳:随机串`，
`credential = base64(HMAC-SHA1(TURN_SECRET, username))`，有效期 `TURN_TTL_SECONDS`；
长期共享密钥只留在服务端环境变量里，前端拿不到它。TURN 服务器必须以同一个 `static-auth-secret` 配置才能验通。
没配 `TURN_SECRET` 时服务端不发凭证（静态 `TURN_USER/TURN_PASS` 已不再下发，见 §7），
`/api/xfer/config` 的 `turnConfigured` 也就是 false，前端不会尝试 TURN、不会白等一轮 ICE 超时。

**配对机制的定位（不夸大）**：这里没有用 PAKE。传输码里真正承担安全的部分是
`secret`（120 bit 随机，字母表 32 个字符 × 24 位），它不是"人类可猜的短码"，
服务器或被中途截获的一方都无法靠枚举把它试出来 —— 猜测空间配上"10 分钟内错 30 次就冻 IP"的限流，
离线字典攻击不成立。E2E 密钥由 ECDH 派生，`secret` 只用来算配对凭证，所以拿到 sid+secret
也不等于能解密。剩下的短板是"主动冒充服务器的中间人"：HTTPS 入口下靠 §3 的 ECDH + 两端人工核对安全码挡住；
`kex='code'`（HTTP 入口）这一档没有 ECDH，页面会明确标出来，此时不能声称独立挡住了主动中间人。

**"同一个局域网为什么还是走了服务器中转"——现在能直接读出来，而且默认就有解了。**
非直连时状态区会打一行诊断：`host N（其中 mDNS M）/ srflx X / relay Y · 选中 local→remote · 原因`。
`host` 是浏览器自己的地址候选；Chrome 默认把 host 候选写成 mDNS 名（`xxxx.local`），
**跨机器能不能解析完全取决于局域网**（Windows 防火墙、AP 隔离、跨 VLAN、访客 Wi-Fi 都会挡）。
`srflx` 来自 STUN；`relay` 来自 TURN。

服务端**自带一个极简 STUN**（`lib/stun.js`，udp `STUN_PORT`，默认 3478），并把
`stun:<你访问页面用的那个主机名>:<端口>` 随 `/api/xfer/config` 下发。两端都向它问一次
Binding，拿到的就是**各自的真实内网 IP:port**——这正是绕过 mDNS 那一层的办法，不需要外网 STUN、
不需要改防火墙的组播策略。它只回一个地址，不转发任何数据。
`STUN_PORT=0` 可关掉（那就退回 mDNS / 自建 `STUN_URLS`）。如果诊断里 `stun` 有值但 `srflx` 是 0，
那是 UDP 出不去（防火墙/安全软件），放行 `STUN_PORT` 即可。
如果 `relay` > 0 且选中的是 `relay→relay`，那是 TURN 在工作，不是"直连失败"。
中转到云端服务器时的吞吐上限取决于服务器与两端带宽；同局域网直连才可能跑到百兆/千兆。

## 5 API（全部挂在 `/api/xfer/`，凭证只走请求头）

| 方法与路径 | 作用 | 鉴权 | 备注 |
|---|---|---|---|
| `GET /config` | 返回 STUN/TURN 是否可用、TTL 等公共配置 | 无 | 不含密钥 |
| `POST /create` | 建会话：`sid, proof, frames, totalBytes` | proof | 返回一次性 sender token（服务端只存其 SHA-256）。无凭证端点，受 `XFER_CREATE_LIMIT` 限速 |
| `POST /join` | 接收方配对 | proof | 失败计数进限流 |
| `GET /events` | SSE：`joined/key/confirm/offer/answer/ice/ack/done/cancelled` | sender token 或 proof | 断线后服务端补发最近一条同类信令 |
| `POST /signal` | 转发一条信令 | 同上 | kind 白名单：offer/answer/ice/key/confirm/channel-ready/xfer-error |
| `GET /turn` | 领取短期 TURN 凭证 | proof/token | 没配 `TURN_SECRET`（含只配了静态账号的情况）一律 503 |
| `PUT /seg?sid&i` | 上传一帧密文 | sender token | 单帧上限 `XFER_MAX_SEG`，并发上限 `XFER_MAX_INFLIGHT` |
| `GET /seg?sid&i` | 拉一帧密文 | proof | 幂等：同一 i 返回同一字节 |
| `GET /state?sid` | 查 uploaded/acked/frames/totalBytes/expiresAt | 任一凭证 | 只回区间，不回内容 |
| `POST /ack` | 接收方上报"已本地落盘"的块 | proof | 这是三档进度里最高的一档。**语义是信任声明**：P2P 直连的块不过服务器，服务端无法验证，能约束的只有协议帧号空间 |
| `POST /done` / `POST /cancel` | 结束会话 | 任一凭证 | 结束后再保留 `XFER_END_KEEP_MS`，然后连目录一起删 |
| `POST /purge` | **立即**销毁并自证：删内存账本、删目录、再查一次目录确实不在 | 任一凭证 | 幂等；返回 `{gone, removed:{segments,bytes}}`。客户端拿到 `gone` 且再查 `state` 是 404 才删本地记录；删除时还"立旗"，在飞的 PUT 不许把目录写回来。孤儿目录（内存里没会话、盘上还有）在每次 `sweep` 里回收 |
| `GET /residue?sid` | **只读残留核验**：这一单在服务器上还剩几段、多少字节、几时到期 | **无** | 返回 `{sid, exists, segments, bytes, state, expiresAt}`，没有内容也没有文件名。无凭证是刻意的：能销毁它的 token/proof 只存在浏览器本地，隐私模式/清站点数据/换机器之后就没了——那时用户除了"相信 TTL"，本来是没有任何可核对的话的。单独限速桶（`XFER_PROBE_LIMIT`） |
| `POST /keep` | 会话续期 | 任一凭证 | 页面开着（含后台节流）时每 5 分钟一次；`expiresAt = min(now+TTL, createdAt+MAX_LIFE)`，到整单上限照样清 |
| `GET /sessions` | 运维视图：状态与字节数 | 无（只含 sid/计数） | 不含文件名、密钥、凭证 |

`sid` 出现在 URL 查询串里（它是传输码公开的那一半），**`secret`、`proof`、sender token 全在请求头或请求体**，
所以反向代理的访问日志最多记到 sid，凭它解不出内容。

接收链接也一样：整码跟在片段里（`transfer.html#recv?code=…`），浏览器不会把 `#` 之后的内容发给服务器；
页面读到码之后立刻 `replaceState` 把地址擦回 `#recv`。手工拼成 `?code=…` 的链接页面同样认，
但那种写法会整条进访问日志 —— HTTP 入口下等价于把解密密钥写进日志，见 §9 第 8 条。

## 7 断点续传的实际做法

**发送端**：本地记录（localStorage）存 `code / expiresAt / frames / totalBytes / safety / kex / token / 会话密钥`
和每个文件的 `{relPath, name, size, sha256, mtime}`。这份记录现在**完整回给界面**（含 keys）——
以前界面只拿得到展示字段，点"续传"时 `send()` 发现 `record.keys` 不存在，直接报"密钥本地已经没了"，
**发送端续传从来没成功过**。重新选文件时逐个核对：清单里没有这个 relPath、大小变了 → 拒绝并说明原因；
**尺寸与修改时间都对得上就沿用上次摘要**（2GB 不再为了续传把盘读一遍），对不上才重算并核对 SHA-256，
内容变了 → 明确拒绝。加密上下文（文件密钥、nonce 规则）完全复用，所以重传字节一致。
会话已过期/被清空时，续传的第一步是查一次 `state`：404/410 直接说"服务器上已经结束（过期或已清空），
需要重新发一次。校验值留在本地，重发不用重算"，而不是挂在一个永远转的"连接中"。

**准备阶段（码先给）**：建会话只需要 `frames / totalBytes`（由文件大小算出），所以先 `create` 把码显示出来，
指纹在后台并行算；清单帧（第 0 帧）发送前才等摘要。2GB 的"解析哈希/切块"不再挡着用户把码发给对方，
码一出现就能配对，指纹算完自动开传；等待期界面显示"正在准备文件指纹 N%（可以先把码发给对方）"。
指纹算法不变：逐 128KiB 一块 SHA-256，整份摘要 = 这些块摘要的链摘要（接收端按同一规则验完整性）。
工作线程按 8MiB 批量读盘；本机 Node 实测 64MB：批量读 343ms（186.6MB/s）vs 逐块读 334ms（191.6MB/s）——
**没有量到提速**，瓶颈在 SHA-256 本身而不是切片次数。批量读保留是因为浏览器里每次 `slice` 要走一次
文件系统边界，但浏览器侧的提速率没有单独量过，不当结论。

**接收端**：只把"已通过 GCM 标签验证的密文帧"写进 IndexedDB（key = `sid#seq`）。
续传时先把本地已有的 seq 认领回来（不重下），清单帧也从本地读回来恢复布局，
然后只向服务器补拉"服务器有、本地没有"的块；三档确认（发送端已上传 / 服务端已记账 / 接收端已落盘）各自独立，
最后一个块落盘后才走 `verifying → ready`。
两处容易漏的账（都是 600MB/48MB 真浏览器跑出来的，不是推想）：
① 落盘确认请求发不出去时要退回缓冲重试，不能"清掉再吞异常"—— 丢一批确认，发送端的 done 门
就永远差这几块，会话不收尾、服务器密文一直占着中转配额；
② 恢复认领本地块之后，要按"本地有、服务器还不知道"的差集**补一次确认**（幂等，不重发整本账）——
刷新前那批"存好了但确认没发出去"的块否则永远没人补。
逐块重算校验时某一块从 IndexedDB 读不回来，也不是"文件坏了"：那一帧服务器手上还有，
先补拉那一帧再继续（详见 §4 那行）。

**生命周期**：短暂断网、SSE 断开、P2P 掉线都只影响通道，不销毁恢复数据。页面开着时每 5 分钟 `keep` 续期
（后台标签页的定时器会被节流但不会完全停），一次续 `XFER_TTL_MINUTES`，但整单不超过 `XFER_MAX_LIFE_MINUTES`
（默认 120 分钟）——到点照样清。真正销毁只发生在：会话过期、任一方 `purge`/`cancel`、完成后超过 `XFER_END_KEEP_MS`。
**"忘记"不再是"只删本机记录"**：先 `purge` → 再查 `state` 必须是 404/410 → 才删本地记录，并把服务器回执
（清掉几块 / 多少字节）显示出来；拿不到回执就保留记录、提示联网后再点一次。刷新之后同样能做：
记录里有 token / code，`purgeSaved()` 不需要活会话。

**保存落盘分三条路**（按"能不能不把整份文件攥在 JS 堆里"排序，接收端点保存时自动选）：
① 有 File System Access（`showSaveFilePicker` / `showDirectoryPicker`）→ 选真实目录，逐块流式写盘；
② 没有 FS Access 但有 OPFS（`navigator.storage.getDirectory`）→ 逐块写进站点私有目录
`xfer-out/`，交回界面的是**磁盘支撑的 File**，JS 侧不再攒整份（浏览器自己怎么读这份 File 不在这条判据里，
进程级内存只能按映像名汇总、会把用户自己开着的 Chrome 算进来，所以不作数）；
③ 两样都没有 → 才退回"明文块攒进 Blob"，这一条会占住整份文件的内存（小文件尚可，大文件不合适）。
因为 ② 落的是**明文**，它有自己明确的清理路径：下载之后 `dropSaved()` 扫干净，
每次新会话开工前再 `sweepSaved()` 兜一次（上一轮没走完就关页也不留）；
120 MB 实测：暂存里确实有那一份（1 个条目 / 120 MB），清完之后 0 条目 0 MB，
留在渲染进程里的明文是 0 MB，下载下来的文件 SHA-256 与源文件一致。

**做不到也要说**：接收端本地暂存上限取决于浏览器给的存储配额；浏览器不支持 IndexedDB 或配额被拒时，
页面在能力横幅里直接写明"接收端断线恢复不可用"；只有走上面第 ③ 条的浏览器保存大文件才会占内存。

## 8 服务端存的到底是什么

`TRANSFER_DIR/<sid>/`：`meta.json`（sid、proof 的 SHA-256、发送方令牌的 SHA-256、帧数、字节数、过期时间、状态）、
`seg-<i>.bin`（一帧密文，文件名是序号，不含原名）。没有明文、没有密钥、没有真实文件名。
配对凭证与发送方令牌都只落 SHA-256：能读到这个目录的人也拿不到可重放的凭证。
权限随进程默认 umask，目录与 `uploads/` 逻辑隔离，正式列表/下载接口读不到它。
重启时 `bootReclaim` 会把"写了一半的 .tmp"清掉、未过期会话保留、账本从磁盘重建（bytes 按磁盘实况修正）。

清理路径：完成 / 取消 / 过期 / 服务重启后的残留 tmp，都有对应代码路径；测试里逐条断言过目录真的消失。

## 9 安全边界（不夸大的部分）

1. **服务器不是不可见**。它知道：有会话、sid、帧数、字节数、时间戳、双方 IP、谁在猜码。
   它不知道：文件名、内容、明文长度之外的结构（128 KiB 对齐会泄露量级，最后一块会暴露文件大小模 128 KiB 的余数）。
2. **`kex='code'` 的降级路径**（HTTP 入口）不建立在 ECDH 上，因此**不能独立挡住一个主动冒充的服务器**；
   此时安全性依赖"传输码的 120 bit secret 没被第三方拿到"。页面在这条路上会明确显示当前不是 ECDH。
   HTTPS 入口走 ECDH + 安全码核对，两边数字一致才认为链路上没有别人。
3. **TLS 不替代应用层加密**，反过来应用层加密也不替代 TLS：HTTP 入口下任何人都能看到 sid 和流量模式。
4. **密文会落盘**。为了支持重启后续传，中转帧写在磁盘上；这等于承认"服务器被取证时密文可被拿到"，
   能不能解开取决于 §3 的密钥有没有离开过两端。
5. **物理擦除不承诺**。删除是逻辑删除（unlink）；SSD 磨损均衡、快照、备份、文件系统残留不在保证范围内。
6. **离线不是完整支持**。双方必须都在线才能推进；发送方离线时接收端只能拿到已经上传的块，会话过期后旧码作废。
7. 传输码是一次性的：会话做完/取消/过期后同一个码不能再开，也不会重发新码。
8. **接收链接就是传输码的另一种写法**。它带完整码（含那 120 bit secret），放在 `#` 片段里所以不进服务器与代理的
   访问日志，页面读完后 `replaceState` 也会把当前历史项擦成 `#recv`（所以浏览器历史里留不下）——
   但**发出去的那条聊天消息 / 邮件本身就是密钥**：`kex='code'`（HTTP 入口）下拿到链接等于能直接解密，
   HTTPS + ECDH 下拿到链接也只能冒充接收方去收密文，还得躲过安全码核对。别把链接发到不信任的群里。
9. **重投为什么不会踩到 nonce**。nonce 是 `f(类型, 文件号, 块号)`，没有随机量：所以"超时重投 / 断线补拉 /
   换通道"对同一块产生的帧是**逐字节相同**的（`protocol.test.js` 里"重传同一块得到逐字节相同的帧"钉着这条），
   幂等由块号收敛。本轮把所有网络调用加上超时、把收尾改成可重投之后，特意回头复核过这一点。
   **剩下的窄缝**：这个"字节相同"依赖"同一块重读出来还是同样的内容"。若发送方在传输途中替换了磁盘上那份文件，
   重投时可能用同一 nonce 加密**不同**明文 —— 端到端那层会抓到（逐块哈希链 + 整文件 SHA 不符 ⇒ 判"内容被人动过"），
   但那是检测、不是预防。本轮没有为此改动架构（要防得给每块带序号+时间戳的第二次派生），
   把它作为已知边界写在这里：**传输过程中不要改源文件**；改了不会被悄悄接受，但代价是那一次的密文不再等价。

**而同一句里过去的 `Error: bad port` 不是负载，已经查到机械成因**：`test/helpers.js` 按
`4600 + pid%300 + slot*37 + attempt*41` 算端口，而 undici 的 fetch 带一份"禁用端口"名单
（这台 Node 24 上，本机公式能走到的区间里命中 6665、6666）—— 命中时**服务端 bind 得好好的，
客户端 fetch 直接抛 `bad port`**，于是凡是算到那两个端口的腿整批变红，和负载无关。
A/B 证明：把端口钉死在 6665 并摘掉新加的守卫 → `downloadstats` 5 条全红在 `bad port`；
守卫装回去 → `bad port` 不再出现。要如实记下：第二刀因为我把端口钉成了常量，
走的是"绕不开就显式报错"那一支，没演成"绕开就绿"，"绕开就绿"只能由真实公式下的自然跑背书。

本轮还抓到两条**工装自己的缺陷** —— 都不是产品缺陷，但它们都会让绿灯说谎：

- **台架嵌套**：`engine-harness.js` 里 `const nativeFetch = g.fetch` 取的是"那一刻的全局 fetch"，
  而第二个台架起来时全局 fetch **已经是上一个台架的注入器**了，于是注入套着往下漏：
  89 号腿（收尾一直拒）留的 `refuseFinish=99` 让 90 号腿每次收尾都吃 409。
  症状形状正是"单独跑绿、接在前一条后面必红"。证据在报错文本里：那一句 409 是
  `还有块没被接收端确认落盘`（**没有数字**）—— 服务器那句一定带数字，只有夹具会发这一种。
  修法：原生 fetch 在模块加载时取一次（`REAL_FETCH`），并加一条守卫"转发目标不许是台架自己的注入器"。
  变异：把那一行打回 `g.fetch` → 后续 19 条腿各自在 330ms 内炸，报"台架嵌套…"；还原后逐字节回到基线。
- **`withLab` 装台架那一步炸了就不停服务**：监听还开着，跑测进程永远等不到端口释放 ——
  上面那把变异就是这么挂了 6 分钟一行结论都没吐。现在 setup 失败也先把服务器关掉再往上抛。

  `open-blind` / `late-blind` / `recv-timeout` / `switch-order` / `no-sess-guard` /
  `degrade-reentrancy` / `no-dedup` / `no-dedup-main` / `ack-drop` / `reverse-read` /
  `no-net-timeout` / `finish-blind` / `no-stall-watch` / `no-self-heal` / `stale-alarm`）。

  续传 `reusable` 恒 false → 只红"不重算指纹"；把 `startHashing()` 改回 `await` → 只红"码先给"
  （轨迹里 fp 已经 1048576/1048576）；不启动 `armKeep()` → 只红"续期请求没发出来（0 次）"。
  每次还原后逐字节核对基线。

### 真浏览器（两台独立上下文）实测，`test/lab/xfer-big-lab.js`

判据打在引擎状态 + 服务器请求计数 + 中转区磁盘 + 独立复算的哈希上，不打在界面文案上。
"端到端哈希一致"这条不看引擎自我声明：另开一路从 IndexedDB 逐帧解开重算哈希链，
再和 Node 在源文件上算的参照值比；带 `--save=1` 时还要下载落盘文件的 SHA-256 也相等。

|---|---|---|
| 600MB 基础 | 通过 | 267.5s、2.24MB/s；4801 帧 / 4801 次 PUT / 线上 600.2MB；接收端 JS 堆峰 4MB；服务器 RSS 峰 149MB；中转区峰值 600MB；done 后目录清空 |

这个假说；真实原因见 §4 与提交记录（可恢复的读失败被当成了永久失败）。

**J / K 两条保存判据自带合成自测**（`node test/lab/xfer-big-lab.js --self-test=1`，不需要浏览器）：
5 个合成读数 —— 健康的、退回 Blob 兜底的、清了个寂寞的、只落了一半的、探针直接读不到的 ——

同一轮还给等待循环加了心跳（每 15s 打 phase/stored/frames/chan/error），下一次卡住能直接看出卡在哪。
旧版只查"清完之后为 0"的 K 在"压根没写进 OPFS"这一刀下是**假绿**（before=after=0 照样通过），
现在 K 必须同时看到"暂存里确实落过 ≥90% 的文件大小"才算数。

### 只算模拟、不算网络证据

台架（`test/lab/engine-harness.js`）里只有 DataChannel 是桩，加密/协议/服务器/账本都是真代码。
它证明的是**引擎的决策逻辑**，不是两台机器真能连通。

### 环境受限 / 未验证（不要当成已通过）

- **真实 P2P 直连与真实 TURN relay 未验**。本机 Chromium 一个 ICE 候选都产不出
  （裸 `RTCPeerConnection` 实测 gathering=complete、候选 0），也没有 TURN 服务器可指。
  上面所有真浏览器跑里 `dcFrames` 都是 0、通道标识如实是 `server_relay` ——
  也就是说：直连/TURN 两条路径的**选路逻辑**有判据，**实际互通**需要两台真设备再验一次。
- **多 GB 的单文件真浏览器端到端没验成**，并且把原因量到了：这台机器当时只剩 4.9~7.3 GB 空闲物理内存，
  同时跑着另一个项目的 headless 验证和两个 dev server。两次跑（2GB 停在 506/16385、1GB 停在 6663/8193）
  都是在"两端页面和实验室自己的 `page.evaluate` 一起不返回"的那一刻冻住，同一次里还伴随
  `Failed to fetch` 与 shell 的 fork 失败（"内存不足"）。
  **这种现场既不能报"产品通过"，也不能据此报"产品坏了"** —— 于是把停摆这一类改成台架里的确定性判据来证
  （挂住的请求、挂死的加密线程各一条，都能变异），GB 级的浏览器吞吐/内存峰值因此**没有数字**。
  600MB 那一跑是同一份代码在拥挤程度低一些时的实测（见上表）。
- **数 GB 单文件的配额与上限是算得出来的、不是测出来的**：`XFER_MAX_FRAMES` 20 万帧 ≈ 25GB，
  配额 6.1GB 的探针只到 600MB；再往上要一台干净的机器复跑。
- **只有 FS Access 和 OPFS 都没有的浏览器**，保存才会退回"整份明文攒进 Blob"（§7 第 ③ 条）。
  这一条本轮**没有真机证据**：能拿到的 Chromium 两样都有，凑不出"都没有"的那个环境；
  兜底路径本身已经按 0MB 残留验过（120MB / 24MB 两跑）。
  `chromeRssPeakMB` 那把尺子按映像名汇总，会把用户自己开着的 Chrome 也算进来
  （同一实验室两次读数差 800MB）→ 它只当上限参考，进程级内存结论一律改用"留在渲染进程里的明文字节"。
- 物理擦除、SSD 磨损均衡/快照/备份残留不在承诺范围内（§9）。

## 11 升级与部署兼容

**旧的 `TURN_USER` / `TURN_PASS`（长期静态账号）怎么迁**

1. 给 coturn 打开 `use-static-auth-secret` + `static-auth-secret=<同一个密钥>`，把它设成 `TURN_SECRET`；
   `TURN_URLS` 照旧。两侧必须是同一个密钥，否则 401。
2. 从环境里删掉 `TURN_USER` / `TURN_PASS`。留着也没用：`/api/xfer/turn` 只认 `TURN_SECRET`，
   没配它一律 503 并在启动日志里打一行提示。
3. 老配置不会"静默变好"也不会"静默变坏"——不配 `TURN_SECRET` 就是没有 TURN，
   直连不通时照旧走服务器密文中转，功能不受影响，只是慢一跳。
4. 为什么不再下发静态账号：`/api/xfer/create` 是无凭证端点，任何人自己建会话就能把这份账号领走，
   等于把一个长期 TURN 凭据公开挂在公网。短期凭证按会话签、`TURN_TTL_SECONDS` 到点作废。

**目录名校验（`^\d{8}_\d{4}(_\d+)?$`）对历史数据的影响**

- 本服务从第一个版本起，落到 `uploads/` 的目录名就一直是 `folderName(now)` = `日期_时间`
  （同分钟撞车时追加 `_序号`），也就是这条正则的子集 —— **服务自己建过的目录没有一个会被新规则挡住**，
  不需要迁移，也没有任何东西被改名或删除。
- 如果 `uploads/` 里混进了别人放的目录（手工拷进去的、别的程序写的），新规则会**忽略而不是删除**：
  不列表、不下载、不打包、不删除，启动日志打一行 `[提示] ... 已忽略`，最多列 5 个名字。
  要留着就自己移到别处；要接进服务，就把它改成 `日期_时间` 的形状（改名是可回滚的一步操作，
  内容不动，服务重启后就会正常列出）。
- 回滚：这条规则只在读/删的路径上"少认"目录，不改写、不移动任何文件；
  回退代码后原来的目录照旧可用。也就是说升级和回退都不产生数据迁移需求。

**日志与反向代理**

- 应用自己不记访问日志（没有 morgan 一类中间件），进程日志只有 `[清理] / [上传] / [无痕] / [证书]` 这些事件行，
  内容不含传输码、proof、发送方令牌、文件名。全局错误处理器只回显 `err.expose` 的文案，不打印堆栈给客户端。
- 传输码只在两处出现：前端 `localStorage`，和接收链接的 `#` 片段（`#` 不进服务器与代理的访问日志，
  页面读完会 `replaceState` 抹掉历史项）。API 里出现过的 `sid` 只到"会话编号"这一层，`sid` 单独拿到不能解密。
- 反代部署要设 `TRUST_PROXY=1`，否则限流按 `127.0.0.1` 记账，所有用户共享同一个猜码/建会话额度桶，
  真实客户端 IP 也就无从记录。
- 中转区 `TRANSFER_DIR` 与 `UPLOAD_DIR` 必须分开；前者只放密文帧与账本，正式列表/下载接口读不到它。

## 12 一次 2GB 现场：慢、断、清不掉

用户的原话归纳成三句：① 一个 2.1GB 的文件传到一半断了，标签页当时不在最前面，**发送方不能重发、接收方不能续传**；
② 本地"解析哈希、切块、加密"要等一会儿；③ 两个人**明明在同一个局域网**，用 HTTPS 入口还是走了服务器中转，实测 4.x MB/s。
外加一句最要紧的：**点"忘记"之后，我没法确认云端那些中转密文到底清了没有。**

这七条都能在代码里指到具体那一行。下面是"现象 → 成因 → 处置"。

| 现象 | 真正的成因 | 现在怎么处置 |
|---|---|---|
| 后台放着就断 | Chrome 的 Page Lifecycle **会冻结后台标签页**：定时器停、SSE 不再读、`pump` 不动。`stallMs`（60 秒）看门狗两次自愈失败后落到 `retrying` —— 界面看起来就是"任务自己没了" | 会话一开始就持一把 **Web Lock**（官方豁免：持有锁的页面不会被冻结）。`caps.locks` 为假（Firefox/Safari）时，能力横幅直接写"大文件别把标签页放后台太久" |
| 断了之后"没法继续、也没法重发" | `retrying`/`failed` 时那颗按钮的文案还是**「暂停」**，点下去等于再停一次；`#start` 被 `liveOf()` 挡着；唯一看上去能走的是"取消并销毁"——听起来像要毁掉已经传了一半的东西 | `paused`/`retrying`/`failed` 三档一律显示**「继续传输」**；取消键在那几档改叫**「放弃这一单并销毁」**（要重发就是"放弃 → 生成传输码"，选好的文件还在）；`failed` 不再冻结操作排 |
| 2GB 走中转必定断 | `XFER_LIMIT_GB` 默认是 **2GB**，而配额判断是"已用 + 这一块 > 上限就 413"。2.1GB 的文件只要最终走中转，**必然在 2GB 处停**，文案还只有一句"中转空间不足" | 默认提到 **8GB**；`create` 回 `limitBytes`/`overBudget`，客户端在开传前就把"这一单比中转上限大"写出来；413 改成"上限多少、这一单占了多少、改哪个开关或走直连" |
| 局域网还走中转 | `STUN_URLS` 默认空 → `iceServers` 为空 → Chrome 只发 **mDNS 主机候选**（`xxxx.local`）；跨机器解析不了就互不可达，8 秒超时降级。**HTTPS 只解决"有没有 WebCrypto"，不解决候选可达性** | 服务端**自带 STUN**（`lib/stun.js`，udp 3478），地址按"你访问页面用的那个 Host"下发 —— 两端都够得着；超时改成**先中转、不掐死 pc**（`lateRtcMs` 120 秒），直连晚到就切回去 |
| 4.x MB/s | 接收端 `pullMissing()` 是 `for..of` + `await`：**一帧一个来回**、128KiB/次；而且每轮拉完固定 `sleep(1500)` 再问下一次，占空比被压到 40% 以下。瓶颈既不是带宽也不是 AES | 并发 **8 路**拉取（块按序号落盘，顺序无关）；**自适应间隔**：上一轮取到过块就 40ms 后再问，空转才退到 1500ms |
| "算哈希要执行一会儿" | 指纹只占了**一条** worker：池里 4 条线程，3 条一直在闲着；2GB 从头读到尾串行算 | 大文件（≥16MiB）按线程数**切段并行**，切点只落在 128KiB 块边界上，拼回来的链摘要与单线程逐字节相同；顺手修掉 `P.cat(...chain)` 在 20 万块时会 `RangeError` 的隐患 |
| "不知道云端清没清" | 能销毁这一单的 `token`/`proof` **只在浏览器 localStorage 里**。隐私模式关窗、清站点数据、换台机器 → 一个字符都不剩 → 既续不了也销毁不了，只能相信一句"30 分钟后会清" | 新增 `GET /api/xfer/residue`：**无凭证**、只回"几段 / 多少字节 / 几时到期"。页面上独立一栏「服务器残留核验」；「忘记」失败时也会自动查一次并如实报出还剩什么 |

**诚实边界（这一轮没解决的）**

1. 内置 STUN 只治"拿不到真实内网地址"这一类。**AP 隔离 / 客户端隔离、两端在不同 VLAN 且三层不通、Windows 防火墙拦入站 UDP** 这几种仍然只能中转或 TURN。诊断行里 `stun` 有值而 `srflx` 是 0，就是最后一类的形状。
2. 并发拉取只是把**接收端自己设的天花板**拆掉；真正的上限还是链路与服务端磁盘。
3. 没有 Web Locks 的浏览器仍会被冻结或直接丢弃；界面会写明，但救不回来。
4. 隐私模式下本地记录仍然会丢，**续传仍然做不到**。`/residue` 保证的是"能确认服务器上有没有"，不是"能续"。
5. `lateRtcMs` 到点仍没建起来的直连会被关掉 —— 不无限挂着一条永远不 open 的 pc。
6. 物理擦除的边界没变（见 §9 第 4、5 条）：`/residue` 说的是"逻辑上还有没有可读路径"。

## 13 又一轮：直连成功之后，界面自己没说真话

用户这次报的是 **P2P 直连已经成功（HTTPS 3443）** 之后的三件事：
① 块进度条一动不动；② 2.5GB 传完，"保存"按钮卡了很久才出现；③ 各种通道/降级模式在界面上长得一样，
分不清到底走了哪条路。顺着这三件事一共摸出六条成因，其中第一条是**样式从来没写**，
而且六条里有三条是**渲染层**的问题 —— 引擎台架完全看不见。

| 现象 | 真正的成因 | 现在怎么处置 |
|---|---|---|
| 块进度条不动 | `progress-strip.css` 的选择器只写了 `#blocks`（发送端/文件库页），**接收端那个 `#r-blocks` 一条规则都没有**：没有 flex、没有格子尺寸、没有配色 —— 600 个 `<div class="blk">` 全是零尺寸空盒子。也就是说接收端那条长条**从第一帧起就没画出来过**，跟"传得慢"无关 | 选择器改成 `#blocks, #r-blocks` 全量覆盖；`test/ui.test.js` 钉住"两个 id 都必须有规则" |
| 发送端也像不动 | 引擎每落盘/发出一块就 `emit()` 一次，界面**每包整页重画**：重建状态行字符串、`innerHTML` 重建模式区、逐个比对 600 个格子。千兆直连下这是每秒上千次重画，主线程被自己的 UI 占满 —— 进度条在等主线程腾出手 | 状态更新合并到 `requestAnimationFrame`（每帧最多一次，状态取最新）；状态行/模式区加内容签名，没变就不写 DOM。DOM 写次数从 O(已传块数) 降到 O(60) |
| 校验卡很久、按钮突然弹出 | `finishReceive()` 是 `for` 里 `await`：2.5GB 两万帧，**一帧一个 worker 来回**，几分钟；而且这段时间界面只有一句静态文案，保存键根本不在页面上 | 复核改成**每批 8 帧并发解密、哈希仍按块序**；新增 `verifyDone/verifyTotal` 帧级进度，长条改画"第二遍扫描"（`.blk.vfy` 绿色从左往右），状态行给出百分比；保存键**提前露出但按不动**（"校验中，还不能保存"），暂停/重连一并置灰 |
| 写盘同样是一句话等到底 | `saveAll()` 也是逐帧串行解密再写 | 同样批量并发解密 + 有序写盘，新增 `saveDone/saveTotal`，按钮变"正在写盘…"并显示百分比 |
| 接收端走中转却写"正在尝试直连" | 发送端有"没走通道就别说是直连"这条规矩，**接收端没有**：它靠 HTTP 拉块，`channel` 只在直连超时（8 秒）时才改。短传输会全程显示"正在尝试点对点直连"，而每一块都是从服务器下来的（真浏览器冒烟实测：长条 100% 时还写着"正在建直连"） | `pullMissing()` 里补上同一条规矩：拉到过块且通道没开 → 如实改成 `server_relay`，但保留 pc（直连晚到仍会切回） |
| 五种模式长得一样 | `turn_relay` 与 `server_relay` 共用 `relay` 一个圆点；"降级"又覆盖了同一个圆点的颜色，于是 HTTP 入口下永远是橙点，反而看不出走的是哪条路 | 圆点只表示通道（绿=直连 / 蓝=本服务器中转 / 紫=TURN / 黄=正在建）；模式区新增 chip 行：**通道 · 加密层(ECDH or 仅口令) · 引擎(原生/纯JS) · 是否降级**，每种通道配一句"快不快、为什么、怎么办" |
| 控制台一条 503 红字 | 服务器没配 TURN 时，`upgradeIceWithTurn()` 仍会去问 `/turn`，拿到 503 —— 读起来像传输出错 | 记住 `turnConfigured`，没配就不再问 |

**这一轮的验证方式换了**：前几轮靠引擎台架（Node 里跑真引擎），但这一轮的缺陷有一半是**渲染**问题，
台架看不见。于是新增 `test/lab/ui-smoke.js`：真 Chromium、真服务器、两个页面上下文，
判据打在**渲染结果**上 —— 格子的 `getBoundingClientRect` 尺寸、`.done` 与 `.blk` 的计算颜色是否不同、
`done` 格子数是否单调增长、保存键在 `verifying` 期间的 `disabled` 与文案、
以及**全程零 console.error**。40MB 实测：321 格、9×12px、`flex`、
颜色 `rgb(0,113,227)` ≠ `rgb(255,255,255)`、done 轨迹 0→321 共 40 个台阶、
保存键 `校验中，还不能保存|true` → `保存到这设备|false`、相位轨迹里能看到 `正在逐块校验`。

**边界**：这台机器（headless Chromium）产不出 ICE 候选，所以冒烟的通道一直是"服务器中转"；
真 P2P 下的**同一套** UI 逻辑没有在这台机器上复现过 —— 但进度条/保存键/模式 chip 的代码路径与通道无关，
而"接收端标识要说实话"这条已被冒烟直接钉住（它正是在中转下暴露的）。
